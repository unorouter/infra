# Incident: L7 DDoS against the unorouter.com zone, 2026-09-03 16:29 to 17:43 UTC

## Summary

An application-layer flood of 507 million requests in 85 minutes (peak 255,000 requests per
second at the Cloudflare edge) took the tunnel and the gateway down in bursts for about 70
minutes. Cloudflare's own DDoS layer blocked 90%; the 5.8 million requests that leaked
through (peak 9,800 per second at origin) were enough, because the attacker retargeted every
few minutes to whatever endpoint the current rules left open and the tunnel pays memory per
open stream. Customer API traffic was interrupted three ways: tunnel down, gateway OOM, and
for four minutes by our own emergency settings (Under Attack mode challenging SDK calls).
No data was lost; 888,978 junk audit rows were written to `logs` and purged afterwards.

Timeline in UTC. The edge configuration itself is encrypted in this repo
(`infra/cloudflare/unorouter.com/rules.sops.yaml`); this document describes what the rules
do, not how they are written.

## Attack vector analysis

Numbers from Cloudflare `httpRequestsAdaptiveGroups`, 16:25 to 17:50 UTC.

| | |
|---|---|
| Requests at edge | 506,892,263 |
| Reached origin | 5,802,735 (1.1%) |
| Peak edge minute | 16:50, 15.3M requests, 255k rps |
| Peak origin minute | 16:57, 590k requests, 9.8k rps |
| Blocked / challenged / passed | 457M / 29.7M / 18.7M |
| Challenges solved by the attacker | 162,644 |
| HTTP/2 | 99.95% |
| Top 1,000 IPs | 421M requests (83%); top IP 2.8M, 1,000th IP 138k |
| Hosts | unorouter.com 261M, api.unorouter.com 192M, status.unorouter.com 54M |

**Sources.** Not a residential botnet: the top ASNs are Datacamp, "High Speed For Internet
Services", Contabo, HostPapa, Oracle Cloud, OVH, DigitalOcean, M247, Microsoft, AEZA, plus
16M requests from Tor exit nodes. About a thousand rented servers, each at 100 to 500 rps,
spread over US, NL, DE, ID, CN, FR, IN, TR, BR. Per-IP rate limiting was therefore effective
on the heavy IPs once it existed (16:50), and useless before.

**User agents.** Ten rotating Windows Chrome and Firefox strings, one fixed headless
signature, and a check-host service the attacker used to verify the outage. The rotation
means user-agent blocking bought one minute at a time.

**Capabilities.** Real browser engines: the attacker solved 162k managed challenges and
Under Attack JS challenges, sent cookies when a rule demanded cookies, sent plausible-looking
keys when a rule demanded keys, and switched hosts and paths within 60 to 120 seconds of
every rule change. This is an operator watching our responses, not a fire-and-forget script.
Assume the operator reads this repository too.

**Targets, in order, and why each one hurt.**

| Time | Target | Why it hurt |
|---|---|---|
| 16:29 | OAuth state endpoint on the frontend, `/sign-in` on the api host | open-and-abort streams; cloudflared OOM at 256Mi |
| 16:33 | api host root (dashboard HTML) | 3k rps leaked, gateway OOM at 2Gi |
| 16:36 | `POST /v1/chat/completions` with junk keys | 401s are cheap, but 30k per 2 min still tied the tunnel |
| 16:53 | frontend root (a 307 redirect) | SSR redirect per request, frontend OOM at 3Gi |
| 16:56 | a locale root page (SSR) | same |
| 17:10 | an authenticated dashboard API path with no credential, both hosts | cheap 401, but one audit row each: 80k rows/min, primary at 3 cores |
| 17:25 | one SSR model page, cookie-less | frontend OOM |
| 17:33 | the status page's data endpoint, with cookies | heavy query per hit, gateway 500 then OOM, three times |
| 17:50 | the public config endpoint on the api host (on the API allowlist by design) | cheap, but 445 rps and 11k abandoned streams; now served from the edge cache |

**The mechanism that mattered** was not request count. cloudflared holds memory per open
stream; the attacker opened requests and abandoned them (edge status 499), reaching 36,000
in-flight streams per replica (normal: ~100) and 106,000 across the tunnel. 256Mi died in one
scrape, 1Gi in under a minute, 2Gi in ninety seconds. A dead tunnel is a full outage even when
every pod behind it is healthy.

## Wave 6, 18:21 UTC: L3/4 SYN flood on node1's public IP (outside Cloudflare)

Hetzner abuse notice: 1.13M packets/s, 432 Mbit/s, 67,703 flows per 5 minutes, spoofed
single-packet sources, direction IN to node1. The kernel logged "Possible SYN flooding on
port 22". Hetzner's mitigation started filtering TCP to that IP: SSH and the API port on
node1 became unreachable from outside while the node stayed Ready on the private network.

What broke for users: CoreDNS ran as a single replica on node1 and forwards through node1's
egress, so for two minutes (18:21 to 18:23) every upstream lookup in the gateway failed with
"server misbehaving" and requests returned 500. node1's conntrack table (default 131k, half
the other nodes) went from ~870 to 95k entries in that minute.

Fixed: CoreDNS now runs 3 replicas, kept off node1 (applied to the live deployment; k3s
re-generates that manifest on restart, so this must be re-applied or moved into a managed
manifest). conntrack limits raised to 2M on all nodes and persisted in the cloud-init
templates. The laptop kubeconfig and the watchdog now talk to node8's API endpoint.

Lesson: Cloudflare only protects what goes through Cloudflare. A node IP was public (DNS for
the Teleport entry) and carried a single point of failure. Since then no node IP is published,
the firewall accepts no inbound TCP, and DNS runs as three replicas kept off that node.

## Why each layer failed, in order

1. **Cloudflare's DDoS managed ruleset defaulted to challenges for many signatures.** Real
   browser engines solve those. Until the override switched the action to block (17:00:49),
   30 million challenges were issued and the solved ones reached origin.
2. **No zone-level rules existed at all** (custom rules, rate limits, config rules were all
   empty), so nothing was ready to enable; every rule was written under fire.
3. **Under Attack mode was enabled by hand at 16:39** with no exemption for the API in place,
   which challenged every `/v1/*` SDK call for four minutes. The traefik-era playbook already
   said this for the other zone.
4. **cloudflared had a 256Mi limit and no GC ceiling**, sized for 50Mi of normal use.
5. **The gateway's security-denial audit wrote one row per refused request** with no cap
   and no distinction between "presented a bad secret" and "presented nothing".
6. **The status page's data endpoint was uncached and expensive**, and the status host had
   no rule at all.
7. **The frontend renders SSR for every hit**, including the root redirect, with no edge
   cache and no bot gate.
8. **Emergency rules had bugs of their own**: the first key check rejected CORS preflight and
   one accepted credential form (a customer was blocked for 10 minutes); the datacenter-ASN
   challenge caught our own nodes (blackbox, sync job).

## What was changed (all in effect now)

**Cloudflare, zone `unorouter.com`, now Pro plan.** Config lives encrypted in
`infra/cloudflare/unorouter.com/rules.sops.yaml`, applied by `apply.sh` (idempotent PUT per
phase). In intent:

- One canonical machine-surface expression, taken from the gateway's router groups (the relay
  prefixes, the public read endpoints, the infra hosts, PAT-authenticated dashboard calls,
  CORS preflight, webhooks, MCP, our own nodes). One skip rule, first in the list, exempts
  exactly that surface from Super Bot Fight Mode, from Security Level challenges and from
  every custom rule below it, so the surface is defined once. The whole set is four custom
  rules and fits the free plan (`CF_PLAN=free ./apply.sh` reshapes the two Pro-only pieces).
- Super Bot Fight Mode on (definitely-automated blocked, JS detections on, verified bots
  allowed). Safe only because of the skip above; SDK clients look "definitely automated" to
  Cloudflare.
- Under Attack mode is scoped by configuration rule to the browser hosts only; the zone level
  stays medium and is never toggled zone-wide again.
- Custom rules: known flood fingerprints blocked; relay paths must carry a plausible API key
  (checked at the edge, in every header form the gateway accepts); Tor, high threat score and
  datacenter networks are challenged on browser surfaces; dashboard API calls that carry no
  credential at all are challenged; browser surfaces are challenged when they carry no
  session; the status host is challenged once per visitor.
- Rate limits: a zone-wide per-IP auto-ban (one-minute window, one-hour block, the Pro
  maximum), sized with several times the headroom of the busiest real customer IP; static
  and Cloudflare-internal paths do not count. Plus a tighter cap on the status data
  endpoint. Re-measure before lowering either.
- Cache rules: the status data endpoint, and anonymous reads of the public config endpoints,
  are served from the edge. Anything on the allowlist that is public and unauthenticated must
  be cacheable, otherwise the allowlist itself is the next target.
- The frontend root redirect is served at the edge. DDoS L7 override: block at the highest
  sensitivity. Cloudflare's managed WAF ruleset runs on browser surfaces only, never on relay
  or API paths (prompts look like injections to a WAF).
- The generic fingerprints (empty User-Agent, forwarded-for chains, HEAD) apply to browser
  surfaces only. A customer's bare HTTP client or reverse-proxy chain on `/v1` is not blocked.
- Two pre-built modes. Normal is what runs day to day. Attack mode adds Under Attack on the
  browser hosts, a challenge for session-less visitors to the frontend, and a tighter
  auto-ban; the API allowlist is exempt in both. Switching is automatic: the `edge-mode`
  Deployment in `monitoring` receives the stream-flood alert from Alertmanager, flips the
  zone within seconds, and flips back 30 minutes after the alert resolves. The same switch
  exists as `apply.sh attack|normal` for a human. The emergency measures that annoyed real
  users (Under Attack on the frontend, the session-less challenge) are therefore off in
  normal mode instead of "relaxed later by hand".
- Credentials: edge changes use a zone-scoped API token (OpenBao), created after the
  incident; the account-wide key used during the response is scheduled for rotation.

**Cluster.**
- cloudflared: 2Gi limit with a Go memory ceiling below it (`infra/cloudflared/cloudflared.yaml`).
- Gateway (`unorouter/new-api`): no audit row for a refused request that presented no
  credential; a per-process budget for the rest.
- `logs`: 888,978 junk rows purged in one transaction with the audit-retention trigger
  disabled and re-enabled inside it (read back: 0 remaining, trigger enabled), then
  `VACUUM (ANALYZE)`.
- Gateway, second build: per-scope in-flight caps (relay and public) that return a fast 429
  once a pod holds too many open requests, and a singleflight cache on the status buckets
  endpoint. A stream flood now degrades to 429s instead of memory growth.
- Frontend: anonymous public pages are marked cacheable by the app and served from the edge
  (session, theme and RSC requests bypass), the locale cookie is gone (it made every
  mismatched-language visit uncacheable), an HPA scales 2 to 5 on CPU, request raised to a
  full core. The frontend runs under Bun, which ignores every Node heap flag; the memory
  ceiling is the HPA plus the cache, not a heap cap.
- CoreDNS: taken over from k3s's bundled manifest into ArgoCD (`infra/coredns`): three
  replicas, spread across nodes, kept off the flood-prone node, PodDisruptionBudget 2 of 3.
  k3s is told to skip its own copy on every server and in cloud-init.
- Postgres: primary moved off the flooded node; autovacuum tuned per table on the two
  large tables and cluster-wide, so the 16 GB `logs` table is vacuumed by Postgres again.
- Alerting: `CloudflaredStreamFlood` pages on open tunnel streams (the leading signal); a
  per-replica warning; the degraded-tunnel alert corrected to the real replica count. The
  alert set was then audited against 30 days of firing history and the rules that only ever
  described normal life were removed, so a page means something.
- Operator plane: Tailscale on all nodes, the netcup box and the laptop, with Tailscale
  SSH and the kube API served over the mesh (k3s certificate SANs added). Teleport's public
  entry IP is gone; the proxy is served through the Cloudflare tunnel instead, with `tsh`
  riding Teleport's WebSocket connection upgrade, so no node IP exists in DNS anywhere. The
  Hetzner firewall no longer allows any inbound TCP: only the Tailscale UDP port and ICMP.
  Break-glass ladder documented in the DR runbook (temporary firewall rule, VNC console with
  root password, rescue mode).
- Repository: the edge configuration and node addresses were committed in plain text to this
  public repo for about twenty minutes during the response, in the window before the SYN
  flood on node1. The commits were removed and the repository recreated so the objects are
  gone; the configuration now lives encrypted (`rules.sops.yaml`) and this document describes
  rules by intent only.

## How we prevent the next one

Done, as of this incident:

1. Edge config is code, encrypted, and pre-built. A new attack starts from the rules above.
2. The API surface is allowlisted by one expression, so any future challenge, bot mode or
   Under Attack toggle cannot touch SDK traffic. Test after any change: an SDK user agent with
   a plausible key against `/v1/models` must return the origin's 401, never a Cloudflare 403.
3. Cloudflare's DDoS layer blocks instead of challenging.
4. Bots cannot make the gateway write to the database anymore.
5. The tunnel survives roughly 10x more open streams than before.
6. The origin IPs are no longer part of the attack surface: nothing listens on them, and
   nothing the product depends on runs only there.
7. Attack mode is automatic and reversible; nobody has to write rules at 3 a.m.

## Reading the blocked-user report next time

"Sorry, you have been blocked" (a plain block page, not a challenge) comes from: a
fingerprint rule, the key check, a rate limit, or the DDoS override. Query Cloudflare
analytics for that IP with `securitySource` and `securityAction`; the source names the
layer. The two false positives seen today were both in the key check.
