# Incident: L7 DDoS against the unorouter.com zone, 2026-09-03 16:29 to 17:43 UTC

## Summary

507 million requests in 85 minutes (peak 255k rps at the edge) took the tunnel and the
gateway down in bursts for about 70 minutes. Cloudflare's DDoS layer blocked 90%; the 5.8M
that leaked through (peak 9.8k rps at origin) were enough, because the attacker retargeted
every few minutes to whatever endpoint the current rules left open, and the tunnel pays memory
per open stream. Customer API traffic was interrupted three ways: tunnel down, gateway OOM, and
for four minutes by our own emergency settings (Under Attack mode challenging SDK calls). No
data lost; 888,978 junk audit rows were written and purged.

The edge configuration is encrypted in this repo (`infra/cloudflare/unorouter.com/`); this
document describes what the rules do, not how they are written.

## Attack vector

Cloudflare `httpRequestsAdaptiveGroups`, 16:25 to 17:50 UTC:

| | |
|---|---|
| Requests at edge / reached origin | 506.9M / 5.8M (1.1%) |
| Peak minute, edge / origin | 15.3M (255k rps) / 590k (9.8k rps) |
| Blocked / challenged / passed | 457M / 29.7M / 18.7M |
| Challenges solved by the attacker | 162,644 |
| Top 1,000 IPs | 421M (83%); top IP 2.8M, 1,000th IP 138k |
| Hosts | unorouter.com 261M, api 192M, status 54M |

**Sources.** Not a residential botnet: Datacamp, Contabo, HostPapa, Oracle Cloud, OVH,
DigitalOcean, M247, Microsoft, AEZA, plus 16M requests from Tor exits. About a thousand rented
servers at 100 to 500 rps each. Per-IP rate limiting worked on the heavy IPs once it existed.

**Capabilities.** Real browser engines: solved 162k managed and JS challenges, sent cookies
when a rule demanded cookies, plausible keys when a rule demanded keys, and switched host and
path within 60 to 120 seconds of every rule change. Ten rotating browser user agents, so
user-agent blocking bought one minute at a time. An operator watching our responses, and this
repository.

**Targets, in order.**

| Time | Target | Why it hurt |
|---|---|---|
| 16:29 | OAuth state endpoint, `/sign-in` on the api host | open-and-abort streams; cloudflared OOM at 256Mi |
| 16:33 | api host root (dashboard HTML) | 3k rps leaked, gateway OOM at 2Gi |
| 16:36 | `POST /v1/chat/completions` with junk keys | cheap 401s, but 30k per 2 min tied the tunnel |
| 16:53 | frontend root (a 307 redirect) | SSR per request, frontend OOM at 3Gi |
| 16:56 | a locale root page (SSR) | same |
| 17:10 | an authenticated dashboard path with no credential | cheap 401, one audit row each: 80k rows/min, primary at 3 cores |
| 17:25 | one SSR model page, cookie-less | frontend OOM |
| 17:33 | the status page's data endpoint, with cookies | heavy query per hit, gateway 500 then OOM, three times |
| 17:50 | the public config endpoint (allowlisted by design) | 445 rps and 11k abandoned streams; now edge-cached |

**The mechanism that mattered** was open streams, not request count. The attacker opened
requests and abandoned them (edge status 499), reaching 36,000 in-flight streams per replica
(normal ~100) and 106,000 across the tunnel. 256Mi died in one scrape, 1Gi in under a minute,
2Gi in ninety seconds. A dead tunnel is a full outage even when every pod behind it is healthy.

## Wave 6, 18:21 UTC: SYN flood on node1's public IP, outside Cloudflare

Hetzner abuse notice: 1.13M packets/s, 432 Mbit/s, spoofed sources, inbound to node1.
Hetzner's mitigation filtered TCP to that IP, so SSH and the API port became unreachable from
outside while the node stayed Ready on the private network. What broke for users: CoreDNS was
a single replica on node1 forwarding through node1's egress, so for two minutes every upstream
lookup in the gateway failed and requests returned 500. node1's conntrack table (default 131k)
went from ~870 to 95k entries in that minute.

Lesson: Cloudflare only protects what goes through Cloudflare. A node IP was public (DNS for
the Teleport entry) and carried a single point of failure. Since then no node IP is published,
the firewall accepts no inbound TCP, conntrack is sized at 2M, and DNS runs as three replicas
kept off that node.

## Why each layer failed

1. Cloudflare's DDoS ruleset defaulted to challenges, which real browser engines solve. Until
   the override switched it to block (17:00), 30M challenges were issued and the solved ones
   reached origin.
2. No zone-level rules existed; every rule was written under fire.
3. Under Attack mode was enabled by hand at 16:39 with no API exemption, challenging every
   `/v1/*` SDK call for four minutes.
4. cloudflared had a 256Mi limit and no GC ceiling.
5. The gateway wrote one audit row per refused request, with no cap and no distinction between
   "presented a bad secret" and "presented nothing".
6. The status data endpoint was uncached and expensive.
7. The frontend rendered SSR for every hit, including the root redirect, with no edge cache.
8. The emergency rules had bugs: the first key check rejected CORS preflight and one accepted
   credential form (a customer blocked for 10 minutes); the datacenter-ASN challenge caught
   our own nodes.

## What is in place now

**Edge (Cloudflare Pro, config in `infra/cloudflare/unorouter.com/`, applied by `apply.sh`).**

- One skip rule, first in the list, defines the machine surface (relay prefixes, public read
  endpoints, PAT-authenticated dashboard calls, CORS preflight, webhooks, MCP, our own nodes)
  and exempts it from bot fight mode, security level and every rule below. Four custom rules
  total; `CF_PLAN=free ./apply.sh` reshapes the two Pro-only pieces.
- Super Bot Fight Mode on; relay paths must carry a plausible key; known flood fingerprints
  blocked; Tor, high threat score and datacenter networks challenged on browser surfaces;
  credential-less dashboard calls and the status host challenged; the managed WAF ruleset on
  browser surfaces only.
- Per-IP auto-ban (one-minute window, one-hour block) with several times the headroom of the
  busiest real customer, static paths excluded; a tighter cap on the status data endpoint.
- Edge cache for the status data, the anonymous public config endpoints, and every frontend
  page the app marks cacheable. Root redirect served at the edge. DDoS override at block.
- Two pre-built modes. Attack mode adds Under Attack on browser hosts, a challenge for
  session-less frontend visitors and a tighter auto-ban; the machine surface is exempt in
  both. The `edge-mode` service flips it on the `CloudflaredStreamFlood` alert and back 30
  minutes after resolve; `apply.sh attack|normal` is the manual equivalent.
- Zone-scoped API token in OpenBao for all edge changes.

**Cluster.**

- cloudflared: 2Gi limit with a Go memory ceiling. Survives roughly 10x the open streams.
- Gateway: no audit row for a refused request that presented no credential, a per-process
  budget for the rest; per-scope in-flight caps that return a fast 429; a singleflight cache
  on the status buckets endpoint.
- Frontend: anonymous pages cacheable and served from the edge, locale cookie removed, HPA
  2 to 5 on CPU with a full core requested.
- CoreDNS managed in ArgoCD, three replicas spread and kept off node1, PDB 2 of 3.
- Postgres: primary moved off node1, autovacuum tuned so the 16 GB `logs` table is vacuumed.
- Alerting: `CloudflaredStreamFlood` pages on open streams, the leading signal; the alert set
  audited against 30 days of history and the noise removed.
- Operator plane: Tailscale on every node and the laptop, kube API and SSH over the mesh.
  Teleport served through the Cloudflare tunnel with the WebSocket connection upgrade. Hetzner
  firewall allows no inbound TCP. Break-glass ladder in the DR runbook.
- Repository: the edge config and node addresses were public for about twenty minutes during
  the response; history was removed and the config now lives encrypted.

## Test after every edge change

An SDK user agent with a plausible key against `/v1/models` must return the origin's 401,
never a Cloudflare 403; a CORS preflight must return 204; webhook and MCP paths must reach the
origin. Then run `mitigations.py`: a webhook sender, CLI client or OPTIONS request in its
output is a false positive. "Sorry, you have been blocked" (a plain block page, not a
challenge) comes from a fingerprint rule, the key check, a rate limit, or the DDoS override;
Cloudflare's security events name the layer.
